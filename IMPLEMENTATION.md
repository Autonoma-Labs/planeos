# Autonoma Environment Factory — integration checklist

Autonoma seeds an isolated workspace of realistic test data before each end-to-end
run by calling one signed endpoint on this app, then tears it down afterwards. This
file tracks that integration: the Django API in `apps/api` serves the endpoint, and
the recipe it seeds lives outside the repo at `~/.autonoma/planeos/recipe.json`.

SDK endpoint path: /api/autonoma

## Time-relative data

Values the app compares against the current clock are **not** stored in the recipe.
The recipe supplies a day offset and the factory adds it to `timezone.now()` at seeding
time, so the data cannot go stale. The fields, and the app query that partitions on
each one:

| Field                               | App query                                                                                                                                                          | Recipe input                       |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------- |
| `Cycle.start_date` / `end_date`     | `CycleViewSet.get_queryset` annotates CURRENT / UPCOMING / COMPLETED; the "active cycle" filter; `CycleIssueViewSet.create` refuses a cycle whose `end_date < now` | `starts_in_days`, `ends_in_days`   |
| `Issue.target_date`                 | `UserWorkspaceDashboardEndpoint` `overdue_issues` (`target_date__lt=now`)                                                                                          | `target_in_days`                   |
| `Issue.start_date`                  | `UserWorkspaceDashboardEndpoint` `upcoming_issues` (`start_date__gte=now`)                                                                                         | `starts_in_days`                   |
| `Module.start_date` / `target_date` | burn-down chart range in `module/base.py`                                                                                                                          | `starts_in_days`, `target_in_days` |
| `APIToken.expired_at`               | token authentication rejects an expired token                                                                                                                      | `expires_in_days`                  |
| `IntakeIssue.snoozed_till`          | intake list separates snoozed from open                                                                                                                            | `snoozed_in_days`                  |

Verified against the seeded data by running the app's own annotations: Sprint 1 →
COMPLETED, Sprint 2 → CURRENT (and the sole match for the active-cycle filter),
Sprint 3 → UPCOMING; "Authentication Flow" in the dashboard's overdue list and "API
Documentation" in its upcoming list; Auth Module spanning now, Dashboard Module in
the future.

`Cycle.description`, `Page` bodies and similar fields nothing filters on stay concrete —
an offset there would only obscure them.

## Per-run uniqueness

Enumerated from the model definitions and from the live database's unique indexes.
Only two constraints are global rather than scoped to a per-run parent, and both carry
a token:

| Constraint                        | Recipe value                                                                                       |
| --------------------------------- | -------------------------------------------------------------------------------------------------- |
| `users.email` (global unique)     | `admin+{{testRunId}}@acme.test`, and the same for the other four users and the three invite emails |
| `workspaces.slug` (global unique) | `acme-{{testRunShortId}}`                                                                          |

Everything else is unique only within a parent that is already per-run — `projects
(name, workspace)` and `(identifier, workspace)`, `states (name, project)`, `labels
(project, name)`, `modules (name, project)`, `intakes (name, project)`, `webhooks
(workspace, url)`, `workspace_member_invites (email, workspace)`, `instance_admins
(instance, user)`, `deploy_boards (entity_name, entity_identifier)` — or is generated
by the app itself: `users.username`, `api_tokens.token`, `deploy_boards.anchor`,
`issue_comments.description_id`, `webhooks.secret_key`.

## Notes and deliberate deviations

**Singletons — the documented concurrency exception.** `Instance` and
`InstanceConfiguration` cannot be created per test run:

- `instances` is a singleton by construction. Every request resolves "this instance"
  with `Instance.objects.first()` (ordered `-created_at`), the API container registers
  it on boot via `manage.py register_instance`, and `instances.instance_id` is globally
  unique. A second row would silently become _the_ instance for the whole process.
- `instance_configurations.key` is globally unique and instance-wide; `manage.py
configure_instance` creates every key on boot.

Both factories therefore **adopt** the existing row instead of inserting one, and both
have a no-op teardown — deleting shared instance configuration would pull the
authentication settings out from under a concurrent run. They only ever write values
that are identical for every run (`is_setup_done`, `ENABLE_EMAIL_PASSWORD`, …), so two
concurrent seeds cannot disagree. `InstanceAdmin` _is_ per-run: it points the shared
instance at a seeded user, and `(instance, user)` keeps that unique.

**`State` is adopted, not created.** Creating a project creates the six
`DEFAULT_STATES`, whose names are exactly the ones the scenario asks for, and
`(name, project)` is unique — in Plane a second "Backlog" in one project is impossible.
The `State` factory adopts the matching row; only a name the project does not already
have is inserted. Adopted rows are left for the project's teardown to remove.

**`workspace_seed` is not dispatched.** `WorkSpaceViewSet.create` queues a Celery task
that fills a new workspace with a demo project, ten issues, cycles, modules, pages and
views, created by a generated bot user. It is not dispatched here: the scenario fixes
the workspace at exactly two projects (Engineering, Marketing) and five users, and the
demo project would contradict that and make every count-based assertion unstable. It
is a background task the entity audit lists separately from the synchronous creation
path, so skipping it does not skip any validation, hashing or derived field. If a test
ever needs the demo data, call `workspace_seed(workspace.id)` synchronously from the
`Workspace` factory and give it a teardown for the bot user.

**Activity and notification tasks are not fired.** The `issue_activity`,
`model_activity` and `notification_task` Celery tasks that a real request queues after
creating a work item are not dispatched. They only write `IssueActivity`,
`Notification` and `IssueVersion` rows — none of which the entity audit assigns to a
factory — and dispatching them would make seeding finish at a nondeterministic time and
race teardown. Every synchronous side effect of the creation path (IssueSequence,
IssueAssignee, IssueLabel, Description, ProjectIdentifier, ProjectUserProperty,
ModuleMember, ProjectPage, Profile, UserNotificationPreference) _is_ produced, because
the real creation code produces it.

**Two inlined inserts were copied rather than called.** `WorkspaceMemberInvite` and
`ProjectMemberInvite` are written inline inside their view handlers, mixed with request
parsing and an invitation email task, and `ProjectInvitationsViewset.create` does not
currently run at all (it calls `.role` on a queryset and shadows the email task with
the local list). Both factories copy the insert verbatim — including the JWT invite
token the accept-invite link carries — and drop the email side effect.

**`FileAsset` has no object-storage upload.** `UserAssetsV2Endpoint.post` inserts the
row and then asks S3 for a presigned upload URL. The insert is reproduced; the
presigned URL is an external-service call with nothing to persist, so the asset is left
`is_uploaded=False`, exactly as it is before a client uploads its bytes.

**The webhook URL must resolve in DNS.** `WebhookSerializer` runs Plane's SSRF check,
which resolves the hostname and rejects private addresses — so a webhook URL on a
`.test` domain fails. The recipe uses `https://webhook.site/acme-plane-notify`, which
resolves and is a service intended for receiving test webhooks. Nothing in seeding
triggers a delivery.

**A few counts exceed `scenarios.md`.** The scenario lists one `ProjectMember`; the
recipe creates four. `IssueCreateSerializer` drops any assignee who is not a project
member with role ≥ 15, so without memberships for Dave and Diane the scenario's
assignee rows silently vanish — confirmed by seeding a slice without them and finding
one `issue_assignees` row instead of four. `State` is 6 per project (12 total) because
project creation makes them for both projects.

**The frontend dev server has a pre-existing failure in this checkout.** `apps/web`
builds and serves fine (`react-router build`, and the built SPA renders Plane's real
sign-in screen against this API), but `react-router dev` returns 500 with
`TypeError: (0 , __vite_ssr_import_5__.jsxDEV) is not a function` — `@react-router/dev`
resolves to 7.17.0 while `react-router` resolves to 7.18.1. This is untouched by this
branch (which changes no JavaScript, `package.json` or lockfile) and does not affect
the integration; Autonoma runs tests against a preview built from the repo's
Dockerfiles, not this dev server.
